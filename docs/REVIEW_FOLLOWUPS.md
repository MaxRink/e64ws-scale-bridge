# Review follow-ups

A code review of this repository listed gaps that were not implemented when the
review was written. Each one is either implemented now or explicitly marked as
unimplemented here, with the place that enforces the limit and the workaround.
Nothing in this list is silently dropped; a change that implements one must
update this table.

That sentence was **not** true before the 2026-11-25 pass. Three review items
were dropped without a row: `--restore` accepted any bytes and only checked
that the backup existed, the grinder's response payload was printed
unredacted, and a rejected `AddBrewEvent` exited 0. All three are fixed and
listed below with the test that pins them, so the claim is now checked by
`tests/test_docs.py` (every item named in `REVIEW_ITEMS` must have a row with
an explicit status) instead of being an assertion about intentions.

Status values: **implemented** (in this repository), **partial** (implemented
with a documented limit), **unimplemented** (deliberate; use the workaround),
**documented trade-off** (behaviour is deliberate and its consequence is
stated where it happens).

| Review item | Status | Where it stands |
|---|---|---|
| Token refresh | **unimplemented** | A token is supplied per run (`--token`, `--token-file`) or obtained once by `--login-role`. There is no background refresh or automatic re-login when the vendor expires the WSS token; an expired or rejected session ends as an error (exit 2). Re-run with a fresh token. The on-device daemon needs no WSS token at all. |
| TLS pinning | **partial** | `--ca-file` trusts exactly the certificate/CA you pass, which pins the device certificate, and `--insecure` disables verification. There is no SPKI pinning and no pin-rotation handling. See the TLS bullets in [GUIDE.md](GUIDE.md#5-replay-and-troubleshooting). |
| WSS reconnect | **unimplemented** in `tools/e64ws_client.py` | One connection per request, closed afterwards; no retry/backoff loop. A silent or dropped connection now ends in a redacted message and exit 2 instead of a traceback (`tests/test_e64ws_client.py:ReceiveTimeoutTests`), and re-running reconnects. The on-device daemon *does* reconnect the scale's `ws://` stream with exponential backoff. |
| Tare | **unimplemented** | `OpenScaleClient.send_safe(..., allow_tare=True)` exists, but no bridge path calls it: the bridge never tares the scale. Use the scale's own tare button/screen. The detector compensates for level changes by re-seeding its idle baseline instead. |
| Invalid-event path for dropout / early removal / retained samples | **partial** | Early removal ends the shot as `cup removed / weight drop` (`tests/test_scale_bridge.py:test_cup_removal_ends_the_shot`); a short shot is reported with `validity: false` (`test_short_shot_is_invalid_but_reported`); a shot that never settles closes at `--max-shot-ms` as `reason: "timeout"` (`test_never_flat_series_times_out_instead_of_hanging`). A **dropout mid-shot is discarded, not emitted**: the daemon resets the detector and returns to idle (`tests/test_ondevice_daemon.py:test_dropout_discards_an_active_shot_and_rearms`, and the routing through `run_forever` in `test_a_stream_that_drops_mid_shot_is_discarded_through_run_forever`), because the samples are incomplete. The detector still **retains the pre-shot idle samples** in its sample list, so `sample_count` counts them; only samples after the `--stable-ms` cutoff feed the finish window. |
| Redaction in ON_DEVICE §Verification 5 | **implemented** | `e64ws_client.redact()` replaces the supplied secret literally, then everything after a `token=`/`access_token=` key (so a token containing `&` is not half redacted), then any `Authorization` value, `Bearer` or not, and the exception chain is cut so the unredacted text cannot resurface (`tests/test_e64ws_client.py:RedactionTests`). The grinder's **response payload** is redacted before it is printed (`ResponsePayloadRedactionTests`, `BridgeResponseRedactionTests`), a failing `socket.send` is wrapped like the connect and recv paths, and `scale_bridge.main` turns an `OSError` into exit 2 instead of a traceback. **The stated reason for the original fix was wrong** and is corrected in the code: websocket-client does *not* quote the URL on a failed handshake — it quotes the response headers and body, and the token leaks because the *server* echoes the Request-URI in a refusal body (reproduced against websocket-client 1.9.2). [ON_DEVICE_INSTALL.md](ON_DEVICE_INSTALL.md#verification) step 5 requires redacting `ingest_token` and token-bearing headers before evidence leaves the device. |
| `/api/v2/*` HTTPS exemption | **documented trade-off** | The exemption exists because the E64 Xenia client is HTTP-only. The consequence is stated where the exception is configured (`ondevice/patch_lighttpd.py`), in the README and in [ON_DEVICE_INSTALL.md](ON_DEVICE_INSTALL.md#why-lighttpd-is-patched): the five local Xenia routes, including the `POST /api/v2/brewratio` write and the `X-Scale-Token` header for `/api/v2/ingest`, travel in cleartext on the LAN. Accepted only on a trusted, isolated LAN. Narrowing the exemption is not implemented because it would break the QEMU-verified client path. |
| `--max-shot-ms` / `--finishing-ms` vs `config.json` | **implemented** (2026-11-25, completed 2026-11-26) | The CLI wins and the config value is the fallback for every shared key (`max_shot_ms`, `finishing_ms`, `timeout`, `path`, **and `host`, `port`, `url`**); the flags default to `None` so "was it given?" is answerable. Every one of them is resolved by `_resolve()`/`_resolve_number()`/`_resolve_text()`/`_resolve_port()` in `ondevice/scalebridged.py`, which is now genuinely the one place that decides, and `CliConfigPrecedenceTests` takes its fixture from `install.sh`'s own heredoc, so the fresh-install case (where the installer always writes `max_shot_ms`) is covered by construction. `port`/`host`/`url` used to bypass the resolver entirely: `"port": "eighty"` was a raw `ValueError` traceback and the daemon never started, and `--port 0` was swallowed by `args.port or ...` and silently replaced by the config value. Both are now the same clean refusal as a bad `max_shot_ms`, including a port outside 1..65535. A `url` is resolved *and validated* by `_split_ws_url()`, the same function `RawWebSocket` uses, so the scheme must be `ws://` (host non-empty, port parseable and in 1..65535); `wss://` is refused with the reason (this client has no TLS and the endpoint is a plain `ws://` LAN peer), and an explicit port 0 is refused instead of being replaced by 80 (`parts.port or 80`, the same swallowing one layer down). Measured before: config `120000` + `--max-shot-ms 30000` gave `120000.0`; config `"port": "eighty"` gave `ValueError: invalid literal for int() with base 10: 'eighty'` with exit 1 and no daemon; `--url ftp://hds.local/snapshot`, `--url ws://hds.local:70000/x` and `--url ws://:80/x` each exited **0** with only `scalebridged: connection error: ...` retry lines, because `run_forever()` catches the `ValueError`. Now each is one line on stderr and exit 1 (`CliConfigPrecedenceTests`, `UrlValidationCliTests`, which runs the real CLI). |
| `--restore` accepted any bytes | **implemented** (2026-11-25) | `validate_config_text()` refuses an empty, binary, brace-unbalanced or directive-free file; `restore()` exits 5, names the reason, leaves the live config untouched and points at the newest complete `lighttpd.conf.vendor.*`, newest by write time (`_describe_snapshots()` sorts on `st_mtime_ns`), not the last name in the directory. Every copy (snapshot, restore point, live config) is tmp + fsync + rename + directory fsync. `RestoreValidationTests` covers truncated, empty, binary and mid-block backups plus a copy that dies mid-file. Measured before: a 39-byte truncated backup restored with exit 0 and bricked the config. |
| Rejected action exited 0 | **implemented** (2026-11-25) | An explicit `success: false` is a refusal: `rejection_reason()` extracts the reason, the CLI prints it to stderr (redacted) and exits **3**, distinct from 2 (never delivered). `tests/test_scale_bridge.py:RejectedActionTests` also pins that a payload *without* the field keeps the old behaviour. Measured before: `{"success": false, "error": "AddBrewEvent not permitted (dev gated)"}` exited 0. |
| Audit flush only claimed | **implemented** (2026-11-25) | `AuditFlushTests` writes the record to a real file handle and reads it back before the handle is closed, and a subprocess variant lets the transport call `os._exit(9)` after the record. Both capture 0 bytes with `sys.stdout.flush()` deleted from `_print_record` and the full record with it. |
| Dead daemon reported "serving" forever | **implemented** (2026-11-25) | `scale_bridge_state()` applies `SCALE_BRIDGE_STATE_FRESH_MS` (10 s) like the ESP path already did, keeps the shot history but drops the phase, and the daemon heartbeats `updated_ms` once a second so a merely-waiting daemon is not called dead. The age is a wrap-aware modulo of the 32-bit window both writers use. Measured before: a one-hour-old state file gave `MA_STATUS 3`. |
| Uninstall left the cleartext exemption installed | **implemented** (2026-11-25) | `ondevice/uninstall.sh` restores through the validating patcher, keeps the running config and puts it back if `lighttpd -t` rejects the result, restarts lighttpd only after validation, says the exemption is **still installed**, leaves `/storage` so the script can be re-run, exits 1, and only prints "Uninstalled." when everything happened. `tests/test_ondevice_shell.py` runs the real script in a throwaway container and now pins each branch of that flow by name: `test_a_config_lighttpd_rejects_is_rolled_back_and_reported` (the safety copy puts the working config back after a rejected `lighttpd -t`, the exemption is still installed, exit 1, and the copy is not left behind in /tmp), `test_a_backup_that_itself_exempts_api_v2_is_not_reported_as_success` (a restore that succeeds but leaves the exemption installed) and `test_the_uninstaller_restores_through_the_patcher` (an instrumented patcher records the invocation, so an inline `cp` would fail the suite). Measured before: exit 0 with the exemption still configured. |
| Rotation of the shot log, the daemon log and the snapshots | **implemented** (2026-11-25, snapshot retention corrected 2026-11-26) | `shots.jsonl` rotates to `shots.jsonl.1` at 4 MiB (`SHOTS_MAX_BYTES`/`SHOTS_KEEP`, bounded at ~8 MiB); `/log/scalebridged.log` rotates to `.1` at `SCALE_BRIDGE_LOG_MAX_BYTES` (1 MiB) on start; the newest `SNAPSHOT_KEEP` (5) lighttpd pre-edit snapshots are kept. "Newest" is by **write time** (`st_mtime_ns`, set when the snapshot is written), and the name is only the tiebreak when the filesystem's clock is coarser than the edit rate: its whole-second stamp and its `.N` counter are compared as **numbers** (`_snapshot_age()`), so `.10` is newer than `.9`. The previous claim was false twice over: `prune_snapshots()` sorted by name while `snapshot()` names by whole second and reused a freed `<base>`/`.N`, so with two edits in one second the newest name sorted first and the newest-but-one revision was deleted (measured: revisions 2,3,4,5,7 kept out of 0..8); and even with a monotonic counter, name order was *text* order, so every snapshot of a run inside one filesystem clock tick past `.9` reordered the window (measured: eleven edits kept 5,6,7,8,10 and twelve kept 5,6,7,8,11 -- the newest revision deleted while an older one survived). `SnapshotRetentionTests` pins write-time order with explicit mtimes and a coarse-clock harness at 8, 9, 10, 11, 12, 20 and 128 snapshots inside one tick, so it no longer depends on how fast the machine is or on the filesystem's timestamp granularity. Reason: `/db` survives signed updates, so an unbounded log is a per-unit disk leak (~12.7 MB/year at four shots a day). |
| Partial config writes in the installer | **implemented** (2026-11-25) | The default config is written to `config.json.new` under `umask 077`, chmodded `0640` and renamed, so a crash cannot leave a truncated live config and the ingest token is never world-readable; an existing `config.json` that is not valid JSON stops the installer instead of being "kept" forever. `InstallerShellTests` runs the real installer; `InstallerSourceTests` pins the sibling-plus-rename write. |
| Dropout handling was only called directly | **implemented** (2026-11-25) | `test_a_stream_that_drops_mid_shot_is_discarded_through_run_forever` drops the fake scale mid-shot and lets `run_forever` discover it; removing the `_connection_lost` call makes it fail with `'serving' != 'idle'`. The older direct-call test is kept (it pins the handler). |
| BLE sample queue grew without bound | **implemented** (2026-11-25) | `BleSource.QUEUE_MAX` (600 samples, a minute at 10 Hz) drops the oldest sample and counts the drops; the end-of-stream sentinel goes through the same path so a full queue cannot block the BLE thread on its final `put()`. `tests/test_scale_bridge.py:BleBackpressureTests`; measured before: 650 notifications left 650 queued. |
| A timeout shot shows up as a long extraction | **documented trade-off** (2026-11-25) | A shot closed at `--max-shot-ms` is written with `validity: false` / `reason: "timeout"` **and** reported through the `finishing_ms` window, so Xenia shows `MA_STATUS=4` with `REAL_EXTRACTION_TIME_MS` equal to the bound (120 s by default). This is new and user-visible. It is deliberate: the alternative is to suppress the finishing window for timeout shots, which would leave a grinder-facing status that never advances for exactly the case the bound exists for. Lower `max_shot_ms` if the value is unwelcome; `invalid` is what the event carries. |
